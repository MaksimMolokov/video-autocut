# Структурированный анализ проекта: Auto Video Editor

> Дата анализа: 2026-06-08  
> Анализ основан на фактическом состоянии кода — без предположений о будущем состоянии.

---

## 1. Краткое резюме

**Проект** — десктопное веб-приложение на Streamlit, реализующее автоматический монтаж видеоматериалов. Пользователь загружает исходные видео и трек, система анализирует качество, выбирает лучшие фрагменты, синхронизирует с музыкой и рендерит готовый ролик. Есть ручной режим разметки и мультивариантная генерация (A/B/C/D).

**Стек:** Python 3.10+, Streamlit, OpenCV, FFmpeg, librosa, scenedetect, MediaPipe, SQLite3.  
**Размер:** ~4500 строк gui.py, 120+ .py модулей, 28 тест-файлов, 20+ YAML-пресетов.

## 3. Бизнес-логика проекта

### Реализованные бизнес-процессы

1. **Отбор качественного материала** — из сырых исходников автоматически выбираются только пригодные для монтажа фрагменты (UMS ≥ 0.55)
2. **Стилевая кастомизация** — пользователь выбирает пресет (F1–F6, ActionSport, Travel, etc.), каждый пресет диктует стратегию отбора, переходы, темп, синхронизацию с музыкой
3. **Платформенная адаптация** — форматы для Reels, TikTok, Shorts, YouTube, Stories автоматически задают разрешение и длительность
4. **Музыкальная синхронизация** — резки синхронизируются с битом или энергетикой трека
5. **Мультивариантность** — одни и те же настройки дают 4 варианта (A/B/C/D) с разными seed-смещениями для сравнения

### Правила принятия решений

| Правило | Условие | Действие |
|---------|---------|----------|
| Качество фрагмента — good | UMS ≥ 0.55 | Включается в отбор |
| Качество фрагмента — backup | UMS ≥ 0.35 | Резервный, если не хватает good |
| Качество фрагмента — rejected | UMS < 0.35 | Полностью исключается |
| Адаптивный порог | < 15 good-фрагментов | Порог снижается до 0.35 |
| Дедупликация | pHash Hamming < 5 | Фрагмент помечается как дубль |
| Покрытие материала | < 1.5× целевой длительности | Предупреждение о нехватке |
| Intro/Outro | — | 0–2 intro + 0–2 outro, до 3с каждый |
| Запрет (ручная разметка) | include_policy = 'forbidden' | Никогда не попадает в рендер |
| Приоритет (ручная разметка) | include_policy = 'required' | score boost + is_must_use = True |

### Статусы и переходы

- `prep_mode`: `None` → `'running'` → `'done'` | `'skipped'` | `'manual'`
- `generation_status`: `'idle'` → `'starting'` → `'analyzing'` → `'rendering'` → `'completed'` | `'failed'`
- `user_approved` (в БД): `NULL` (не просмотрен) | `1` (одобрен) | `0` (отклонён)

## 5. Алгоритмы

### Алгоритм 1: Анализ видеоматериала (Pipeline)

**Назначение:** Извлечь и оценить все пригодные фрагменты из исходников  
**Входные данные:** Список видеофайлов, папка проекта, флаги уровней анализа  
**Основные шаги:**
1. Для каждого видео — проверить кэш (hash файла в БД)
2. Если не кэшировано — `SceneDetector` → список сцен (start_s, end_s)
3. `QualityAnalyzer` → метрики по каждой сцене (резкость, яркость, движение, стабильность, цвет)
4. Опционально: `ContentAnalyzer` (MediaPipe) → лица, персоны, тип кадра
5. Опционально: `ClipTagger` (CLIP) → семантический тег
6. `ClipScorer` → UMS + стилевые оценки
7. `DuplicateDetector` → pHash, найти дубли
8. `SceneMerger` → склеить смежные сцены, убрать дубли
9. Сохранить в SQLite

**Условия:** Параллельное выполнение (ProcessPoolExecutor по видеофайлам)  
**Результат:** Фрагменты в БД с 38 метриками  
**Проблемные места:** ProcessPoolExecutor не работает при запуске из stdin

---

### Алгоритм 2: UMS-оценка (ClipScorer)

**Назначение:** Единый балл качества фрагмента 0.0–1.0  
**Входные данные:** Метрики сцены (sharpness, stability, brightness, motion, colorfulness, composition_score, action)  
**Основные шаги:**
1. Техническое качество = 0.35·sharpness + 0.25·stability + 0.20·brightness + 0.20·contrast
2. Содержательность = 0.40·motion + 0.30·action + 0.30·complexity
3. Уникальность = 1.0 если не дубль, иначе снижается
4. Финальная композиция = 0.50·saliency + 0.50·rule_of_thirds
5. UMS = взвешенная сумма всех компонентов, нормализация в [0, 1]

**Стилевые оценки:** cinematic, action, social, premium, travel — каждый с собственными весами  
**Результат:** quality_score (UMS) + 5 стилевых оценок  
**Проблемные места:** Веса жёстко прошиты в коде, не вынесены в конфиг

---

### Алгоритм 3: Построение таймлайна (TimelineBuilder)

**Назначение:** Составить финальный список клипов для рендера  
**Входные данные:** Кандидаты из БД, пресет стратегии, результаты анализа музыки, ограничения (MontagePool)  
**Основные шаги:**
1. `apply_montage_pool()` → убрать forbidden, поднять priority
2. Стратегия (`ClipSelectionStrategy`) → взвешенная оценка каждого кандидата
3. `DiversitySelector` → убрать слишком похожие соседние клипы
4. `OrderingEngine` → упорядочить (хронологически / best-first / energy-curve / story-arc)
5. Intro/Outro → применить правила (до 2 intro + до 2 outro)
6. Music sync → подогнать длительности к биту/энергетике
7. Variant constraints → применить seed_offset для A/B/C/D

**Условия:** Целевая длительность ± 10%  
**Результат:** Список `SelectedSegment` (source_path, start, end, role, score)  
**Проблемные места:** Если материала недостаточно, алгоритм не предупреждает до финального рендера

---

### Алгоритм 4: Анализ музыки (MusicFragmentAnalyzer)

**Назначение:** Разбить музыкальный трек на фрагменты по типам  
**Входные данные:** Аудиофайл (MP3/WAV)  
**Основные шаги:**
1. librosa → beat_times, onset_strength, RMS energy curve
2. Сегментация по пикам энергии и битовым маркерам
3. Классификация каждого сегмента: intro / buildup / drop / peak / calm / loopable / outro
4. Расчёт energy_score, rhythm_score, montage_score

**Результат:** Список music_fragments с типами и оценками, сохранённых в БД  
**Проблемные места:** Не работает если аудиофайл очень короткий (< 10с) или нетипичного формата

---

### Алгоритм 5: Ручная разметка (ManualSegmentsStore)

**Назначение:** Сохранить и применить пользовательские временные метки  
**Входные данные:** source_file, start_time, end_time, теги, приоритет, политика  
**Основные шаги:**
1. Пользователь выставляет Mark In / Mark Out через слайдер и number_input
2. Создаёт фрагмент или запрет через кнопки
3. `ManualSegmentsStore.add_segment()` → сохраняет в `.videoeditor/manual_segments.json`
4. При переходе в рендер: `get_forbidden_ranges()` и `get_required_ranges()` → в MontagePool

**Политики include_policy:** required, recommended, optional, backup, forbidden  
**Результат:** MontagePool с forbidden_ranges и priority_ranges  
**Проблемные места:** Нет валидации пересечений (можно создать overlapping required + forbidden)

## 6. Данные и структура информации

### Схема базы данных

```
source_files ──< fragments ──< duplicates
render_history (отдельная, не связана с fragments)
music_fragments (привязка к аудиофайлу, не к source_files)
```

### Таблица `fragments` — центральная сущность (38 колонок)

| Группа | Поля |
|--------|------|
| Идентификация | id, source_id, start_s, end_s, duration_s |
| Техническое качество | sharpness, brightness, contrast, motion, stability |
| Расширенные метрики | colorfulness, complexity, camera_motion_type |
| Композиция | composition_score, temporal_coherence, saliency_score |
| Содержание | has_face, has_person, scene_type, scene_tag |
| Оценки | quality_score, cinematic_score, action_score, social_score, premium_score, travel_score |
| Кропы | crop_16_9, crop_9_16, crop_1_1 |
| Пользователь | user_approved, user_priority, tags (JSON) |
| Пути | thumbnail_path, preview_path |

### Таблица `music_fragments` (21 колонка)

audio_file, audio_hash, start_s, end_s, duration_s, fragment_type (intro/buildup/drop/peak/calm/loopable/outro), energy_score, rhythm_score, beat_clarity, montage_score, reason, warnings, selected_by_system, selected_by_user, excluded_by_user, status (best/recommended/optional)

### Таблица `render_history` (11 колонок)

id, project_dir, style_id, style_name, music_path, created_at, output_path, quality_avg, clip_count, duration_s, user_rating

### Где создаются / изменяются данные

| Данные | Создаются в | Изменяются в |
|--------|-------------|--------------|
| `fragments` | `pipeline.py` → `_analyze_one_video()` | `analysis_db.py` при повторном анализе |
| `music_fragments` | `_run_prep_analysis()` | Пользовательский выбор в Step 2 |
| `render_history` | После каждого рендера | `user_rating` при оценке |
| `manual_segments.json` | `_show_video_markup_block()` | Редактирование/удаление сегментов |

### Потенциальные проблемы с данными

- **Нет версионирования схемы БД** — при изменении структуры таблиц старые БД ломаются
- **`source_path` в `manual_segments.json` — абсолютный путь** → при переносе проекта теряется связь
- **`thumbnail_path` / `preview_path`** — абсолютные пути, аналогичная проблема
- **`user_rating` в `render_history`** — сохраняется, но нигде не используется в алгоритмах
- **`music_fragments` не связана с `source_files`** — нет FK на основную схему

```
    └──────────┬───┘  └───────┬──────────┘
               │              │
    ┌──────────▼──────────────▼──────────┐
    │           SQLite (analysis_db.py)  │

    └──────────────────┬─────────────────┘
                       │
    ┌──────────────────▼─────────────────┐

    │    subprocess → FFmpeg CLI         │
    └──────────────────┬─────────────────┘
                       │

```

### Ключевые технические характеристики

- **UI-фреймворк:** Streamlit (перерисовка при каждом взаимодействии)
- **Состояние:** `st.session_state` (в памяти процесса) + частичный persist в JSON
- **Параллелизм:** `ProcessPoolExecutor` для анализа видео, синхронный рендер
- **Кэш:** SQLite + file-hash для инкрементального анализа
- **Рендер:** FFmpeg CLI (subprocess), команды строятся конкатенацией строк
- **Нормализация видео:** 30 FPS, yuv420p (H.264-совместимый pixel format)

### Пресеты (20+ конфигураций)

Каждый пресет — YAML-файл в `presets/` со следующей структурой:
- `dynamic_level`: slow / balanced / fast / custom
- `clip_selection`: min/max duration per segment
- `transitions`: type (cut/fade/crossfade/flash/blur/zoom), duration, randomize
- `speed_effects`: slow_motion / speed_up factors
- `color`: style (cinematic / natural / warm / high_contrast)
- `music_sync`: mode (beat_sync / dynamic_sync / simple_tempo)
- `audio_selection`: mode (auto_highlight / auto_energy / auto_balanced / manual_range)
- `export`: format, resolution, quality

### Сложные для изменения места

- `gui.py` — 4500 строк монолит, UI и бизнес-логика перемешаны
- `ffmpeg_renderer.py` — FFmpeg-команды строятся конкатенацией строк, нет абстракции над параметрами
- `storage/schema.sql` — нет миграций, изменение схемы требует ручного патча БД
- `clip_selection/strategies/` — каждая стратегия — отдельный файл с дублированием базовой логики

## 8. Проблемные места

### Критические

| Проблема | Где | Риск |
|----------|-----|------|
| Нет миграций БД | `analysis_db.py` + `schema.sql` | Обновление сломает существующие проекты пользователей |
| `gui.py` — монолит 4500 строк | `src/gui.py` | Невозможно тестировать UI-логику изолированно |
| Абсолютные пути в данных | `manual_segments.json`, `thumbnail_path` | Перенос проекта = потеря связей |
| Состояние только в session_state | Весь UI | При перезагрузке страницы — частичная потеря состояния |

### Архитектурные

- **Нет разделения UI и бизнес-логики** — функции типа `_show_wizard_step2()` содержат и UI-код, и алгоритмы
- **`show_material_prep_section()` — мёртвый код** — существует в gui.py, но никогда не вызывается (заменена на `_show_wizard_step2`)
- **`variant_profiles.py`, `easy_mode/`** — выглядят незавершёнными, слабо интегрированы
- **Mood-sync, visual-match-sync** — реализованы частично, не подключены к основному потоку рендера

### Нестабильное поведение

- **ProcessPoolExecutor из Streamlit** — spawn-mode может не наследовать sys.path в некоторых окружениях
- **FFmpeg команды строками** — нет экранирования спецсимволов в путях (пробелы, кириллица могут ломать команды)
- **Адаптивный порог качества** — при малом количестве материала порог снижается автоматически, что может приводить к попаданию некачественных фрагментов

### Технический долг

- Два разных `clip_scorer.py` в `src/preprocessing/` и `src/clip_selection/` с дублирующейся логикой
- Дублирование логики фильтрации в `_dt_apply_filter()` и `apply_montage_pool()`
- `user_rating` из render_history нигде не используется в алгоритмах
- Комментарии на русском и английском языках вперемешку по всему проекту
- Несколько documentation MD-файлов в корне (`ARCHITECTURE_ANALYSIS.md`, `AUTO_RENDER_IMPLEMENTATION.md`, `IMPLEMENTATION_STATUS.md`) — нет единого актуального документа

## 10. Итоговое описание проекта для дальнейшей переработки

### Что проект делает сейчас

Локальный инструмент автоматического монтажа видео. Пользователь указывает папку с исходниками и музыкальный трек. Система анализирует видео (качество, содержание, дубли), отбирает лучшие фрагменты по выбранному стилевому пресету, синхронизирует с музыкой и рендерит готовый ролик через FFmpeg. Есть ручная разметка, фильтрация черновика, мультивариантная генерация.

### Реализованные процессы

- Полный пайплайн анализа: scene detection → quality metrics → UMS scoring → dedup → scene merge
- 20+ стратегий отбора клипов с кастомизируемыми весами
- Музыкальный анализ: сегментация трека, типы (intro/drop/peak), beat-sync, energy-sync
- Ручная разметка с политиками (required/forbidden) и интеграцией в рендер-пайплайн
- 7 платформенных пресетов (Reels, TikTok, Shorts, YouTube, Stories, Website Hero)
- Мультивариантный рендер (A/B/C/D через seed_offset)
- Инкрементальное кэширование анализа в SQLite (по hash файла)

### Ключевые данные

Таблица `fragments` (38 полей) — центральная сущность. Всё строится вокруг неё: от анализа до финального рендера. `music_fragments` обслуживает музыкальную сторону. `render_history` хранит историю рендеров с пользовательскими рейтингами (пока не используются в алгоритмах).

### Технические части

Streamlit UI-монолит (gui.py, 4500 строк) + Python-модули (preprocessing, clip_selection, music_sync, timeline, presets) + SQLite (кэш анализа) + FFmpeg CLI (рендер).

### Видимые проблемы

1. `gui.py` — монолит, бизнес-логика и UI перемешаны, сложно тестировать и развивать
2. Нет миграций БД — обновление схемы ломает существующие проекты
3. Абсолютные пути делают проект непереносимым между машинами
4. Мёртвый код (`show_material_prep_section`), незавершённые модули (mood-sync, easy_mode, visual_match_sync)
5. Дублирование логики оценки в двух разных `clip_scorer.py`
6. `user_rating` в render_history — данные собираются, но не используются

### Что уточнить перед переработкой

- Нужна ли web/облачная архитектура или остаётся локальный инструмент
- Нужна ли multi-user поддержка с авторизацией
- Механизм обучения на рейтингах пользователей (данные есть, логики нет)
- Стратегия миграции существующих БД пользователей при изменении схемы
- Какие пресеты реально используются (нет аналитики использования)
